PROJECT: MEMEID

The Identity and Verification Layer for Solana Meme Coins

Act as a senior Solana blockchain engineer, full-stack architect, security engineer, and product designer. Build MemeID as a production-oriented, mainnet-ready application with real blockchain transactions, live data, persistent storage, and genuine integrations.

Do not build a mockup, landing page only, simulated dashboard, or fake blockchain explorer.

The application must use real Solana mainnet data and actual on-chain transactions. Never fabricate transaction signatures, token addresses, verification badges, market prices, holder counts, liquidity figures, or risk scores.

If an integration requires API keys, access permissions, or a partnership, implement the supported integration interface and clearly mark the missing dependency. Never pretend an unavailable integration is live.

1. PRODUCT VISION

MemeID is a Solana meme coin identity and verification protocol.

Its purpose is to let meme coin creators establish a verifiable identity for their project before launching a token.

Creators should be able to:

* Create or upload their project’s logo.
* Generate structured project metadata.
* Mint the logo as an NFT on Solana mainnet.
* Register the creator wallet.
* Link the identity NFT to the actual token mint.
* Publish a publicly accessible identity page.
* Make identity and risk information available to external launchpads, explorers, and trading bots.

Initial integration targets:

1. Bags.fm.
2. Meteora.
3. Solana trading bots and analytics platforms.

Do not claim official partnerships without confirmation.

The platform must distinguish identity verification from financial safety. An NFT registration is not proof that a token is legitimate, safe, or profitable.

6. NFT IDENTITY MINTING

Use Metaplex Core for the identity NFT unless a verified interoperability requirement justifies another standard.

The minting flow must:

1. Validate the project metadata.
2. Upload the image to durable storage.
3. Upload the metadata document.
4. Verify that both resources can be retrieved.
5. Prepare the actual on-chain mint transaction.
6. Display the expected network fee and any applicable platform fee.
7. Require explicit wallet approval.
8. Submit the signed transaction to Solana mainnet.
9. Wait for appropriate confirmation.
10. Verify the resulting asset using an independent blockchain read.
11. Save the actual asset address and transaction signature.
12. Publish the identity record only after successful verification.

The creator must remain the owner of the identity NFT unless they explicitly authorize a different arrangement.

Never mint an NFT using a hidden server wallet without explicit disclosure and authorization.

Do not silently add royalties, transfer restrictions, or other plugins.

Use the appropriate NFT standard’s metadata capabilities and verify that the NFT is compatible with the intended indexing and discovery systems.

The NFT must not be presented as an official Bags.fm or Meteora credential.

7. IDENTITY REGISTRY

Create a persistent registry connecting each identity record to its NFT and creator wallet.

Each record should contain:

* Project ID.
* Identity NFT address.
* Creator wallet.
* NFT owner.
* Original image hash.
* Original metadata hash.
* Metadata URI.
* Registration timestamp.
* Transaction signature.
* Linked token mint, if available.
* Launchpad, if verified.
* Verification status.
* Record version.

Where practical, anchor the registry relationship on-chain using a suitable established mechanism or a carefully audited program.

Do not deploy a custom Solana program unnecessarily.

If a custom registry program is required, implement a deterministic PDA-based registry with explicit authorization, account validation, and replay protection. Test it thoroughly and audit it before production use.

Never claim an on-chain registry exists until the program has actually been deployed and its addresses verified.

For an MVP, a signed off-chain registry with publicly verifiable evidence can be used while the on-chain registry is being developed.

8. TOKEN LINKING AND VERIFICATION

Create a token-linking workflow.

The creator enters an actual Solana token mint address.

The application must independently retrieve and verify:

* Token mint account.
* Token program ownership.
* Token metadata, where available.
* Mint authority.
* Freeze authority.
* Relevant Token-2022 extensions.
* Actual transaction history where supported.
* Creator wallet’s relationship to the registered identity.
* Any supported launchpad origin information.

Require the authenticated creator wallet to sign the linking request.

A wallet signature proves control of that wallet, not that the signer is a particular real-world person or the original token deployer.

If the relationship between the NFT creator and token creator cannot be independently established, display that limitation.

Check whether the token address is already linked to a different identity.

Detect duplicate registrations, conflicting claims, and suspicious reuse of project identities.

Do not automatically award a verified badge merely because a creator submitted a token address.

Provide separate statuses:

* Identity Registered.
* NFT Verified.
* Token Address Verified.
* Creator Relationship Verified.
* Metadata Integrity Verified.
* Launchpad Origin Verified.
* Risk Assessment Available.

Every status must have a documented verification method.

10. RUG RISK ANALYSIS

Build an evidence-based token risk engine.

Inspect relevant risk signals:

* Mint authority status.
* Freeze authority status.
* Token-2022 extensions and transfer restrictions.
* Liquidity depth.
* Liquidity concentration and withdrawal permissions, where observable.
* Largest token holders.
* Concentration of supply among related accounts.
* Developer and creator wallet activity.
* Suspicious funding relationships.
* Coordinated wallet activity.
* Large or unusual sell transactions.
* Rapid liquidity changes.
* Metadata changes.
* Token launch history.
* Available pool and launchpad information.

Distinguish observed facts from inferred relationships.

For each finding, include:

* Severity.
* Evidence.
* Source account or transaction.
* Detection time.
* Confidence.
* Explanation.
* Data freshness.

Build a transparent risk score from 0 to 100.

Define whether a higher score means greater risk or greater safety. Prefer a clear RISK SCORE where higher values mean greater observed risk.

Document the scoring methodology.

Do not label a token safe merely because no suspicious activity was found.

Do not claim that an account is controlled by the developer unless there is reliable evidence.

If the available evidence is incomplete, display “Insufficient data” rather than a misleadingly precise score.

The platform must not promise guaranteed rug-pull detection or guaranteed protection from losses.
